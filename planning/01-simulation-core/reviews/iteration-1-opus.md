# Architectural Review: 01-simulation-core Implementation Plan

This is a strong plan. The purity discipline, three-clock separation, event-sourcing shape, and the decision to put the independence rule in a single shared validator are all correct and well-justified. The research backing is unusually thorough and the acceptance criteria are concrete. What follows is where the plan has gaps, ambiguities, and latent footguns that will cost the implementer (or split 06) real time if not nailed down now.

## Critical gaps (will block or silently corrupt later splits)

### 1. `now` provenance is unspecified, and this breaks the determinism guarantee it claims
Section 8 says `dispatch(state, action, now)` calls `advanceToNow` first, then reduces. Section 2 and the spec insist the complete record is "seed plus the ordered action log." But `now` is wall-clock input that is NOT part of the action, and it directly drives settlement (timeout fires inside `advanceToNow`). That means the action log alone does not reproduce state: two replays with the same action log but different `now` values settle differently. The replay story only works if every `now` is captured in the log as part of each action record.

The plan never states that `now` is logged. It must. Define the canonical record as an ordered list of `(action, now)` pairs, or fold `now` into the action envelope. Acceptance criterion 1 ("same seed + same action log run twice gives strictly equal state") is under-specified until this is resolved, because "action log" has to include the clock samples. This is the single most important thing to fix.

### 2. `now` monotonicity is assumed but never enforced across the dispatch boundary
`advanceToNow` clamps negative *elapsed* within a single call, but nothing stops a later `dispatch` from passing a `now` earlier than a stored `scheduledAt` that already fired, or earlier than `endsAt` after settlement, or earlier than the previous call's `now`. The shell pulls `now` from `Date.now()`, which is NOT monotonic (NTP steps, manual clock changes, DST is fine but user clock edits are not). The plan should store a `lastNow` high-water mark in state and clamp every incoming `now` to `max(now, lastNow)`. Without it, a backward system-clock jump between two wakes can un-expire a mission in the player's favor, or produce events processed out of order relative to a prior call. Section 7's "negative elapsed clamps to zero" only covers the within-call delta from a stored start, not cross-call regression.

### 3. Snapshot determinism vs. frozen input is internally contradictory for branches
Section 11 says `snapshot(state)` deep-freezes the state including rng, and `runBranch` "steps branch time over the same reducers used by live play." But those live reducers thread RNG immutably by returning a new state (`{...state, rng: nextRng}`). You cannot run a reducer that returns a mutated-shape state against a deep-frozen input unless the branch runner first makes a working mutable clone from the frozen snapshot. The plan implies this ("seeds a branch context from the frozen snapshot") but never states that the frozen snapshot is the untouched comparand and the branch operates on a separate unfrozen clone. Make explicit: freeze is the oracle for the "live state unchanged" test; the branch runs on a deep clone. Otherwise the first reducer call throws in strict mode.

### 4. The branch reducers "share live rules where the operation is shared" but no mission exists yet
Section 11 and the finale depend on branch projections of deliveries/passengers/payments/confidence. Those metrics come from the mission reducers (03-05), which do not exist in this split. The test-double mission emits only "deliver N of M tokens" plus one consequence. So in this split the branch runner can only be tested against test-double semantics, and the real `BranchProjection` shape (openExceptions, deliveries, passengers, payments, confidence) is asserted against missions that are not here. The plan should state explicitly that this split delivers the branch *framework and determinism guarantees* against the test-double, and that the concrete projection computation is a seam filled by 06 pulling on mission selectors. Right now Section 11 reads as if full projections are buildable now; they are not. Flag the dependency so 06 does not discover a half-built `runBranch`.

## Correctness and edge-case footguns

### 5. Consequence folding order is nondeterministic across mission orders
Section 8: "when a mission starts, fold every settled consequence not yet in appliedConsequences for that mission." Consequences cap magnitude, but if two prior missions each emit `flightsDisrupted`, the folded result depends on the order they are applied unless the fold is commutative and associative. The requirements say "apply each preceding consequence once and cap its effect." With capping, `min(cap, a+b)` is order-independent but `cap(a) then cap(b)` composed may not be. The plan must specify: consequences are folded in a canonical order (sorted by `ConsequenceId`), and the capping function is defined over the *aggregate* not pairwise. Otherwise mission-order invariance (acceptance criterion 3) can fail subtly: the story chronology is identical but the *mechanical* initial conditions differ by application order. This deserves an explicit property test: same set of prior outcomes in any order yields identical folded initial conditions.

### 6. "Settled consequence not yet in appliedConsequences for that mission" — the marker key is ambiguous
`appliedConsequences: ConsequenceId[]` is a flat list, but a consequence must be applied once *per subsequent mission*, not once globally. If `commsDelayed` from mission A must affect both mission B and mission C, a single global `ConsequenceId` marker applied when B starts would prevent it ever applying to C. The marker must be keyed `(consequenceId, targetMissionId)`, not just `consequenceId`. Section 8's phrasing ("apply-once markers") and the `ConsequenceId[]` type are too coarse. This is a real bug waiting to happen; the type should be `AppliedMarker[] = {consequenceId, missionId}[]` or a composite string key.

### 7. CHECK SOURCE replies scheduled on the mission clock, but completed checks "persist across missions"
Section 5 and the spec both say CHECK SOURCE schedules a desk reply on the mission clock, yet completed checks persist in the case file across missions and failures. Edge case: a player requests a source check, the mission times out before the reply event fires. Does the pending reply resolve, drop, or carry? If the reply event is in the mission queue and the mission settles/timeouts, Section 7 drains events with `scheduledAt <= now` and then settles. A reply scheduled after `endsAt` never fires. So a check requested late can be permanently lost, yet the spec implies players can rely on checks persisting. Decide and document: either late replies resolve immediately at settlement (deterministically), or the UI must prevent requesting a check that cannot complete before the deadline. The finale also lets the player "request the field report during the finale" — that path needs its own schedule semantics since the finale has its own clock. Specify where a cross-mission pending check lives (campaign-level `sourceChecks`, not mission-level queue) so it survives settlement.

### 8. `receiptTime`/`eventTime` as seconds-of-day cannot cross midnight
Section 5 stores story times as "seconds-of-day integers." The fixture is 21:14 and the whole incident is minutes long, so this is fine for seed one, but seeds two and three "anchored to different minutes" could in principle wrap past 24:00:00 if an author picks a late anchor. Comparators and ordering break at the wrap. Either document that all seeds stay within one day and validate it in the seed fixture test, or store an absolute story-second offset from a seed epoch. The cheap fix is a seed-load assertion that all story times are monotonic and within `[0, 86400)`.

### 9. Floating-point in metrics but the plan only bans transcendentals, never adopts integers for sim math
Research section 1 correctly flags that `Math.sin/exp/pow` etc. diverge across engines, and the plan says avoid them in sim logic (Section 4 mentions nothing about this; it is only in research). But the bank mission's confidence feedback loop and the branch projections will do arithmetic. The plan should promote the research finding into an architecture principle: sim-affecting quantities (confidence, liquidity, capacity) are integers or fixed-point, and any division uses a defined rounding rule with an ID-stable tie-break, never raw floats compared for equality. Section 6 mentions "numeric tuning (channel capacities, liquidity, confidence thresholds)" with no statement about their numeric type. Across-browser determinism is a stated hard requirement; this is the most likely place it silently breaks. Add it to Section 2.

### 10. Deep-freeze of RNG state plus "reconstruct the generator per call"
Section 4 says the wrapper reconstructs the pure-rand generator from serialized numeric state per call, keeping snapshots plain JSON. Good. But confirm `nextInt` never mutates the input `RngState` object (it must return a new one), because branch snapshots are frozen and the live state is shared. If the pure-rand reconstruction reads the frozen array and the wrapper accidentally writes back, you get a throw in branches and a determinism leak in live. Worth an explicit test: calling `nextInt` on a frozen `RngState` succeeds and returns a new object.

### 11. `nextInt(min, max)` with no stated inclusivity or rejection-sampling guarantee
Section 4 gives `nextInt(rng, min, max)` as "uniform integer draw" with no statement of inclusive/exclusive bounds or modulo-bias handling. pure-rand's `unsafeUniformIntDistribution` is unbiased and inclusive; the wrapper should document which and delegate rather than doing `% range` (which biases). Trivial but it is the kind of thing a later author gets wrong when they reimplement. Pin it.

## Save/migration concerns

### 12. Valibot schema duplicates `CampaignState` and will drift
Section 10 validates with "a Valibot schema mirroring CampaignState." Two independent definitions of the same shape (the TS interface and the Valibot schema) drift the moment a field is added in a mission split. Prefer deriving the TS type from the Valibot schema via `InferOutput`, so there is one source of truth and the compiler catches omissions. The plan should mandate schema-as-source-of-truth, not "mirroring," which invites exactly the divergence Section 13 lists as a risk.

### 13. Migration pipeline validates *after* migrating but never validates the pre-migration input shape
Section 10: "parse, migrate, validate." If a v1 save is corrupt in a way that a v2 migration function assumes a field exists, the migration throws before validation catches it. Migration functions are typed `(unknown) => unknown` (good, defensive), but the plan should state each migration must itself be total/defensive and that a throw anywhere in parse/migrate/validate falls through to backup. Section 10 says failures fall primary→backup→fresh, so this is probably covered, but make it explicit that *migration throws* are caught, not just parse/validate throws.

### 14. Backup write "only after confirmed good primary write" plus "QuotaExceededError drops the backup slot" can leave a stale backup newer-than-primary situation
If primary write succeeds, then a later primary write fails on quota and the retry drops the backup and retries primary, you can end up with primary = new, backup = old-but-valid. On next load, primary is fine, so backup staleness is harmless. But if primary is then corrupted and you fall to backup, you silently roll back to an older campaign state — which could *unsettle a mission* from the player's perspective. The monotonic-merge guard (Section 10) is what saves you here, and the plan does mention it, but it must be stated that the merge guard runs on the *backup* path too, not only the primary path. Confirm the recovered-backup load also passes through monotonic settlement merge so a rollback cannot resurrect an unsettled mission.

### 15. localStorage is synchronous and single-key; the backup write is a second key, so the pair is not atomic
Section 10 writes primary then backup as two `setItem` calls. A crash, quota error, or tab kill between them is explicitly the design intent (backup lags primary), which is fine. But note that `JSON.stringify` of the whole `CampaignState` on every debounced write is O(state size) and runs on the main thread; with a few KB it is negligible, so no action needed, just confirming it was considered. The real watch item is that the plan nowhere bounds `CampaignState` growth — `cluesFound`, `inspectedRecords`, `sourceChecks`, `settled`, `appliedConsequences` all grow monotonically and the queue is drained, so the save stays small. Good, but add an assertion/test that a full-campaign save stays under a sane byte budget so a future mission author padding `body: string[]` into persisted state does not blow quota on mobile Safari.

## Determinism-harness and testing gaps

### 16. The "run-twice state hash" needs a canonical serializer, which is not specified
Acceptance criterion 1 and Section 13 rely on hashing canonical serialized state. `JSON.stringify` does NOT guarantee key order across all object shapes in a way you want to depend on (it preserves insertion order, which your reducers must therefore keep stable — a hidden invariant). The plan's "collections are arrays sorted by stable ID" (Section 2.6) handles arrays, but plain objects (like `preferences`, or a mission substate record) rely on insertion-order stability. Either specify a canonical stringify (sorted keys recursively) for the *hash* only, or state that every object in state has a fixed authored key order and add a test. Also note `-0` vs `0` (research flags it) survives `JSON.stringify` as `0` but `Object.is` distinguishes them; `toStrictEqual` in Vitest treats `-0 !== 0`. If any arithmetic can produce `-0`, the run-twice `toStrictEqual` can fail where the hash passes, or vice versa. Normalize `-0` to `0` at state boundaries.

### 17. fast-check action-log generator is the hard part and is under-described
Acceptance criterion 1 wants "fast-check property across arbitrary valid action logs." Generating *valid* action sequences for a phase machine (menu→mission→debrief→finale→ended) with per-phase legal actions is non-trivial and is exactly where `fc.commands` (model-based testing, cited in research) belongs. The plan mentions fast-check but does not commit to the model-based approach or define the command set. This is a meaningful chunk of work; call it out in Section 13 as effort, and specify that the arbitrary must also generate `now` values (monotonic, see gap 2) since `now` drives settlement. An action log without generated clock samples does not exercise timeout paths at all.

### 18. No stated test for the consequence-order invariance or the mission-order chronology invariance beyond acceptance prose
Acceptance criterion 3 ("all six mission orders produce identical story-time chronology") needs a concrete test that runs all 6 permutations and asserts the story-time record graph is byte-identical, AND (per gap 5) that the folded mechanical initial conditions are order-independent where the design intends. The plan should enumerate the 6-permutation test explicitly; it is cheap and it is the guarantee the whole campaign rests on.

## Smaller items worth adding

- **Section 8, forfeit path.** The interface has `evaluate(state, cause: 'completed'|'timeout'|'forfeit')` but the campaign `dispatch` section never shows the forfeit action (End Mission) or how it routes to settlement. The spec requires "confirm End Mission before recording a final forfeiture," which is a shell concern, but the engine needs an explicit `forfeitMission` action that the plan does not list in Section 8's action handling. Add it.

- **Section 6, decoy and "one independent OBSERVED record" guarantee.** The finale requires exactly one independent OBSERVED record about emergency scope. Each seed must be *authored* to contain exactly one such record (the decoy / field report). The plan should state a seed-validation invariant: every seed contains at least one record satisfying `isIndependentObservation` for the run under test, else the finale is unwinnable. Add this to the walkthrough-fixture mechanical check in Section 6 so an authoring error fails a test, not a playthrough.

- **Section 7, 30-minute catch-up cap interacts with CHECK SOURCE persistence.** If a tab is backgrounded for an hour, catch-up clamps to 30 minutes. Fine for the 8-minute mission (it times out). But a pending cross-mission source check with a story-authored "visible wait" must still resolve deterministically on return, not be swallowed by the clamp. Confirm source-check resolution is event-queue-driven and survives the clamp (it should, since the event fires well within any mission window), or document it.

- **Section 9, `MissionModule<S,A>` generics vs. the save schema.** The campaign holds `activeMission: MissionRuntime | null` with "mission substate." That substate `S` is mission-specific and opaque to the engine, yet it must round-trip through the Valibot save schema (Section 10). You cannot write a static Valibot schema for an open-typed `S`. Specify how mission substate is validated on load: either each mission module exposes its own Valibot schema the save layer composes by `activeMission.id`, or substate is validated loosely (passthrough) and the mission reducer re-validates. The plan's "schema mirroring CampaignState" silently ignores that a chunk of CampaignState is mission-defined and not knowable here. This is a real interface gap that 03-06 will hit; resolve it in the mission-module interface now by adding a `saveSchema` (or `parse`) member to `MissionModule`.

- **Section 12, public API omits forfeit, acknowledgeDebrief, newCampaign, selectExtendedTime.** The listed surface (`createCampaign, dispatch, advanceToNow, trace, requestSourceCheck, snapshot, runBranch, selectors, save..., seed catalog`) routes most state change through `dispatch`, which is consistent, but then `trace` and `requestSourceCheck` are called out as separate entry points while debrief-ack and forfeit are not. Either everything player-driven goes through `dispatch` (preferred, since Section 8 calls dispatch "the single choke point") or the API list is incomplete. Note that `trace` returning both a `TraceResult` and "the inspected marker to merge into campaign state" (Section 5) means `trace` is NOT pure-query — it mutates `inspectedRecords`. That contradicts "pure query, no state change" in the spec. Resolve: either `trace` is a selector and a separate `markInspected` action goes through dispatch, or `trace` returns a new state. The current plan has it both ways.

## Summary judgment

The spine is sound and the hard-won determinism lessons from research are correctly internalized. The plan is let down in exactly the places where a headless engine gets quietly wrong: the `now` sample is not part of the replayable record (gap 1), cross-call clock regression is unguarded (gap 2), consequence application is keyed too coarsely and its fold order is unspecified (gaps 5, 6), the save schema cannot statically cover mission-opaque substate (mission-module gap), and `trace` is specified as both pure and stateful. Fix gaps 1, 2, 6, and the `MissionModule.saveSchema` seam before coding; they are cheap now and expensive after 03-06 are built on top. The rest are tighten-the-spec items that will save a test-debugging afternoon each.
